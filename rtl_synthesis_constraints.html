RTL, Synthesis & Timing Constraints

From behavioral intent to gates, with an executed SKY130 mapping and explicit timing assumptions.

What you will learn
  • Read RTL as a description of state and logic, then inspect what synthesis actually inferred.
  • Trace a small, executed mapping into SKY130 cells and distinguish logical proof from timing closure.
  • Build an explicit timing environment and review false-path and multicycle exceptions.
  • Connect digital constraints to analog input slew, loading, reset behavior, and physical implementation.

Where this fits · the flow map is lesson 8

In the flow
step 2, RTL and simulation and step 3, synthesis, with constraints that stay in force through step 8, extraction and timing.
Tools
Verilator and Icarus Verilog for simulation, Yosys with ABC for synthesis, OpenSTA with an SDC file for timing. Commercial: VCS or Xcelium, Design Compiler or Genus, PrimeTime.
Why it matters
Mistakes in the RTL or the constraints are copied faithfully into silicon.

1. RTL describes behavior; a flow chooses an implementation

Register-transfer-level code describes how values change and what state must be retained. Synthesis elaborates parameters and hierarchy, converts processes into registers and combinational operations, simplifies expressions, and maps the result into a target library. The result depends on the available cells, tool options, optimization goals, and constraints. Source-code length is a poor estimate of gate count or delay.

A functionally correct netlist can still have excessive capacitance, poor slew, an unconstrained input, an unsafe clock crossing, or an unrouteable placement. Synthesis, functional equivalence, static timing, and physical verification provide different evidence. Keep their conclusions separate. The Yosys cell-library tutorial describes the technology-mapping stage.

2. Infer the hardware you intended

Consider a two-bit enabled register:

always @(posedge clk)
    if (en) q <= a ^ b;

On an enabled rising edge, each output bit captures the XOR of its input bits. When en is low, the register retains its previous state. That retention is intentional sequential behavior; it is not an accidental combinational latch. The code requests no reset, so the startup value is not specified before an appropriate enabled capture.

In combinational logic, every output must receive a value on every possible path unless a latch is intended. A missing assignment in an always @* or always_comb process can infer storage; the process keyword alone does not eliminate the problem. Use complete assignments and review synthesis messages. Blocking assignments are normally used for combinational calculation and nonblocking assignments for edge-triggered state updates, with deliberate exceptions explained in the design.

RTL constructPossible hardwareReview question
Enabled registerEnabled flip-flop, or ordinary flip-flop plus input selectionWas the desired enable behavior preserved? Was clock gating separately requested?
Incomplete combinational assignmentLevel-sensitive latchIs retaining the old value intentional?
Fixed-bound loopReplicated or optimized combinational logicHow much parallel hardware did elaboration create?
Array with reads and writesMemory macro, distributed logic, or flip-flop bankDoes the selected flow have a compatible macro and port behavior?
ArithmeticAdders, multipliers, comparators, or optimized constantsAre width, signedness, truncation, overflow, and latency defined?

Widths are part of the specification. Storing 15 + 1 in four unsigned bits produces zero after truncation. Explicitly extend operands and preserve a fifth result bit when a carry is needed. Likewise, a signed comparison is not the same operation as an unsigned comparison. Verify boundary values before interpreting an area report. Simulation-only delays such as #5 do not request a reliable five-nanosecond ASIC delay element.

3. An executed SKY130 mapping

The supplied enabled_xor.v implements the example above. The reproduction script reads the bundled SKY130 HD TT/25°C/1.8 V Liberty file, runs synth -noabc, maps storage with dfflibmap, and maps combinational logic with abc -liberty. The reference manifest records its pinned OpenROAD-flow-scripts revision and SHA-256.

Observed, not predicted: Yosys 0.52 produced two sky130_fd_sc_hd__xor2_1 cells and two sky130_fd_sc_hd__edfxtp_1 cells. The reported sum of library cell areas was 77.5744 µm². Both output bits passed the Yosys functional-equivalence check against the Liberty Boolean/sequential models.

The published cell footprints are 11.04 × 2.72 µm for edfxtp_1 and 3.22 × 2.72 µm for xor2_1. Their four-cell footprint sum independently matches that area.

The enabled flip-flop's published next-state function is (D&DE) | (IQ&!DE). Its DE input controls data retention. In the observed netlist, both CLK pins remain connected to the original clock. There is no separate integrated clock-gating cell; internal power behavior still depends on the enabled cell's circuit and characterization.

This result is more useful than assuming that every if (en) creates the same gate pattern. Another library, exclusion list, tool version, or optimization goal may choose a different equivalent implementation. Cell-area sum is not core area: it excludes placement whitespace, clock buffers, physical-only cells, routing, power distribution, and block-level margins.

From learning/labs/L05_mixed_signal_integration, reproduce the optional synthesis example offline after installing Yosys with ABC:

python3 synthesis_example/run_synthesis.py
# If the tools are not on PATH:
python3 synthesis_example/run_synthesis.py \
  --yosys /path/to/yosys --abc /path/to/abc

The script writes a mapped netlist, logs, and an observation record under run_results/synthesis/. Reference evidence is under results/. The bundled library is checked before use. No SDC-driven optimization, STA, placement, routing, clock-tree synthesis, or power estimation was executed for this example. The equivalence proof establishes the modeled logic relationship; it does not establish a clock frequency or silicon behavior.

4. Constraints state the environment the circuit must meet

A timing tool needs more than a clock period. It needs clock relationships and waveforms, external input arrivals, output requirements, slew or driving-cell assumptions, loads, uncertainty, and valid operating modes. The OpenSTA command reference documents the SDC commands. Confirm the units in the library and tool configuration: the bundled example uses nanoseconds and picofarads.

The separate example.sdc states a hypothetical 100 MHz interface. It was not executed in the recorded synthesis run. Its central assumptions are:

create_clock -name core_clk -period 10.0 \
  -waveform {0.0 5.0} [get_ports clk]
set_clock_uncertainty -setup 0.20 [get_clocks core_clk]
set_clock_uncertainty -hold 0.05 [get_clocks core_clk]
set data_in [get_ports {en a[0] a[1] b[0] b[1]}]
set data_out [get_ports {q[0] q[1]}]
set_input_delay -clock core_clk -max 2.50 $data_in
set_input_delay -clock core_clk -min 0.40 $data_in
set_input_transition 0.10 $data_in
set_output_delay -clock core_clk -max 2.00 $data_out
set_output_delay -clock core_clk -min -0.20 $data_out
set_load 0.020 $data_out

The maximum input delay says data may arrive 2.50 ns after the reference edge; the minimum says it may arrive as early as 0.40 ns. These are external arrival assumptions, not delays that the tool inserts into silicon. Output delay reserves time for the external receiving interface. A negative minimum output delay can represent a positive external hold requirement: with zero external trace/skew terms, a 0.20 ns receiver hold gives −0.20 ns. Derive these values from the actual interface, including board and clock relationships.

The 0.020 pF load is 20 fF per output, and 0.10 ns is the assumed input transition. Neither is a generic SKY130 default. An analog comparator with a slow output edge or a sampled-capacitor load that switches in time may require a richer interface model than these constants. Check the library's transition convention before translating a measured waveform into an STA input.

5. Read a path as arrival versus requirement

Timing paths include input-to-register, register-to-register, register-to-output, and purely combinational input-to-output paths. Clocks and asynchronous control pins also have checks, including clock-gating, reset recovery/removal, and minimum pulse width. Review both maximum and minimum delay; a fast path can fail hold even when setup has abundant margin.

For Figure 3's assumed zero-skew setup example, arrival is 0.30 + 2.10 + 0.45 = 2.85 ns. Required time is 10 − 0.12 − 0.20 = 9.68 ns, giving 6.83 ns setup slack. Now consider a separate minimum-delay scenario: 0.08 ns minimum clock-to-Q plus 0.02 ns logic and 0.01 ns wire gives 0.11 ns arrival. If capture-clock lateness is 0.08 ns, hold is 0.06 ns, and hold uncertainty is 0.02 ns, the hold requirement is 0.16 ns. Hold slack is −0.05 ns. Lengthening the period does not repair that same-edge violation.

Use the actual early/late scenarios and edge polarities, propagate slew and capacitance, and revisit the path after routing and clock-tree construction. Lesson 26 works through exact SKY130 timing-table values; the arithmetic here is deliberately independent of the XOR mapping.

6. Exceptions change the question the timer asks

A false path says a timing relationship should not be checked. It does not make a circuit reliable. A multicycle path changes which launch/capture edges are used. It does not insert registers or prevent an unintended early capture. Every exception needs a functional reason, narrowly defined endpoints, and a review of what it removes from analysis.

Tempting shortcutWhy it can be wrongBetter evidence
False-path every net between asynchronous domainsCan conceal bundled-data settling or physical CDC requirementsReviewed crossing architecture, constrained control chains and explicit data bounds
False-path all resetsCan hide recovery/removal on releasePer-domain reset architecture and documented reset checks
Mark a slow combinational block multicycleThe receiver may still capture on the next edgeProven enable/data-stability protocol and inspected edge relationships
Add an exception because slack is negativeChanges the analysis without changing the failureRepair the design, implementation, or incorrect interface assumptions
Use a broad wildcard without checking matchesMay select nothing or remove unrelated pathsFail on unexpected collection sizes and report exception coverage

For one specific same-clock example, suppose a verified protocol launches a word and permits capture only three cycles later, keeping the relevant source data stable. A common SDC pattern is setup multicycle 3 with hold multicycle 2 on exactly those endpoints. The paired hold adjustment restores the intended minimum-delay edge relation under that convention. Different clocks, phases, latches, or -start/-end choices require explicit edge analysis; “N and N−1” is not a universal recipe. Merely having an enable pin is insufficient justification.

For CDC, a synchronizer's asynchronous first-stage input is a different problem from its timed interstage path. Keep the latter short and analyzed. The integration lab demonstrates a stable-data handshake and documents the additional physical constraints that its digital simulation cannot prove.

7. Close the loop between analog assumptions and digital reports

Before accepting a report, check that every expected clock and endpoint is covered, the intended mode is active, and no missing model has become an accidental black box. Inspect representative paths and the worst paths; check transition, capacitance, fanout policy, pulse width, and unconstrained endpoints. Confirm that exceptions matched the intended objects after synthesis renamed or optimized registers.

Then connect the assumptions to physical evidence. A 20 fF load assumption must include the receiver and relevant interconnect. A reference-ready input must have a defined digital threshold, rise/fall behavior, and clock-domain treatment. Supply droop can slow cells; a typical-corner proof does not cover all supply and temperature states. A logically equivalent clock-enable implementation can change clock power and switching noise seen by a nearby analog block.

Solved checkpoint — The enabled XOR maps correctly and passes equivalence. Can we claim it runs at 100 MHz because example.sdc contains a 10 ns clock?

No. The example SDC was not used in the recorded mapping and no STA was run. Even a successful pre-layout timing report would need its library corner, slew/load assumptions, modes, clock treatment, and physical limitations stated. The evidence here supports the four-cell mapping and the Boolean/sequential equivalence result. A 100 MHz requirement remains a requirement until the relevant implementation checks support it.

Check your understanding — an SDC file defines only the clock. What is missing for an input that comes from another chip?

An input delay: how late, and how early, the data arrives at the pin relative to the clock. Without set_input_delay the timer assumes an idealized arrival, so the input path is not checked against the real environment. Outputs need set_output_delay for the same reason.

Key takeaways

  • Inspect inferred and mapped hardware; equivalent RTL can have several valid implementations.
  • Widths, initialization, reset semantics, and enable behavior belong in the functional specification.
  • Timing constraints model the surrounding system and must include early as well as late behavior.
  • False and multicycle paths require protocol evidence; they are not timing-repair commands.
  • Report executed synthesis, equivalence, STA, and physical verification as distinct results.
